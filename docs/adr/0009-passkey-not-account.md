# ADR 0009: a candidate gets a passkey, not an account

## Status

Accepted.

## Context

`UserRepository` exists and is real — but only admins have rows in it
(`User.role: Literal["admin"]`). A candidate never registers, never logs in,
and never receives a JWT the way an admin does. Instead, `POST
/i/{slug}/claim` takes a short passkey (`generate_passkey()`,
`apps/api/src/interviewer_api/passkeys.py`) and returns a session-scoped
token good for that one interview.

## Decision

The candidate's credential is the pair `(slug, passkey)`, generated by the
admin when the invite is created and handed to the candidate out of band
(email, message — outside this system). No signup form, no password, no
email verification, no account the candidate manages afterward.

Why not an account:

- **There is nothing for a candidate account to own.** One interview, tied
  to one invite, expires or exhausts (`InterviewInvite.max_sessions`,
  `is_claimable`) on its own schedule. A returning candidate for a second
  role gets a second link, not a login to an existing profile — the two
  interviews should not be linkable to each other from the candidate side.
- **A password is a liability with no matching benefit here.** Password
  reset flows, hashing, breach exposure — all real cost — for a credential
  used exactly once, for one session, by someone who may never return.
- **The lockout PRD §8 asks for is per-slug, not per-account**
  (`PasskeyLockout`, `PASSKEY_MAX_ATTEMPTS`/`PASSKEY_LOCKOUT_MINUTES`) —
  brute-forcing a passkey locks that invite, which is the actual asset
  worth protecting, not a candidate identity that does not otherwise exist.

## Consequences

- `POST /i/{slug}/claim` never reveals *which* failure occurred (locked vs.
  wrong passkey say the same thing) — there is no account-recovery flow
  that would need to distinguish them for the candidate's benefit, so the
  uniform answer costs nothing and denies an attacker a signal.
- The session token is bearer, in-memory-only on the client
  (`apps/web/CONTEXT.md`'s invariant: never `localStorage`), and scoped to
  exactly one `Session` row — it authorizes turns and finish for that
  interview and reads nothing else, including no `/admin` route.
- A second `claim` on the same slug is a second `InterviewInvite.used_count`
  spend, not a resume — `claim()` always opens a new `Session`. Resuming an
  in-progress interview across devices is unbuilt; it would need the invite
  to distinguish "give me a fresh session" from "give me my open one" rather
  than always consuming a slot, which is a change to `InviteRepository`, not
  a reason to introduce candidate accounts.
